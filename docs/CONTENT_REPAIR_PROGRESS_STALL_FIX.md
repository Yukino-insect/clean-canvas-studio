# 内容修复任务进度停在 1% 的问题与修复方案

## 问题现象

在“内容修复”页面中，用户完成 OCR/手工区域确认并冻结 `MaskPlan` 后点击“运行”，任务列表会进入“处理中”，进度通常显示为 `1%`，随后长时间不再变化。实际修复子进程可能仍在运行，也可能已经完成，因此该显示无法反映真实执行状态。

## 影响范围

- 内容修复页面的图片和视频任务队列；
- 使用 `multiprocessing.Process` 执行的 `ContentRepairProcessor`；
- 由 `ContentRepairMessageBridge` 将进度、日志和预览从子进程转发到 Qt 界面的链路。

画质增强页面不经过这条子进程消息桥，因此不受此问题影响。

## 根因

进度链路如下：

```text
HomeInterface（先显示 1%）
    -> ContentRepairProcessor 子进程
    -> multiprocessing.Queue（进度/日志/预览消息）
    -> ContentRepairMessageBridge 消费线程
    -> Qt progress_signal
    -> 任务列表
```

原实现中，父线程在 `process.join()` 返回后立即调用 `ContentRepairMessageBridge.stop()`。`join()` 只说明子进程已经退出，并不意味着父进程中的消费线程已经处理完队列内的消息。`stop()` 会让消费者在处理完当前消息后退出，队列末尾的实际进度消息（例如 `25%`、`50%`、`100%`）因而被丢弃。界面保留下来的，便是运行开始时由界面主动设置的 `1%`。

动态 OCR 还有第二个独立原因：它会先完整扫描视频、在采样帧或每一帧上运行 OCR，再进入修复和编码阶段。旧实现虽然在扫描循环中计算了 `0–50%`，却只修改 `ContentRepairProcessor.progress_total` 字段，没有调用进度监听器。GUI 因此收不到扫描阶段的任何事件；扫描结束后修复阶段又以 `0–100%` 单独计算，进度语义不连续。首次 PaddleOCR 初始化发生在第一帧检测中，这会进一步放大“任务长期停在 1%”的观感。

## 解决方案

1. `ContentRepairMessageBridge` 保存队列消费者线程，并新增 `wait_for_finish()`。
2. 子进程在 `content_repair_process()` 的 `finally` 中发送 `FINISH` 消息；该消息位于同一生产者此前发送的进度、日志和预览消息之后。
3. 父线程在子进程退出后等待消费者读到 `FINISH`，而不是立即停止消费者。这样，`FINISH` 之前的所有消息都会先被转发到 Qt 信号。
4. 仅在用户中断或等待超时时，才调用 `stop()` 作为兜底，避免异常终止的子进程使消费者线程永久阻塞。
5. 动态 OCR 的定位扫描不再占用任务百分比。定位阶段每推进约 `10%` 会在日志中报告“正在扫描文字位置”，并在完成后明确记录“开始逐帧修复与编码”；只有真正修复并写出视频帧时，任务百分比和预览时间轴才会更新。这样时间轴不会在画面尚未输出时提前跳动。

修复后的收尾顺序为：

```text
子进程发送全部更新 -> 子进程发送 FINISH -> 父线程等待消费者完成 -> 更新任务最终状态
```

动态 OCR 的正常反馈轨迹为：

```text
日志：初始化动态 OCR -> 定位扫描 10% / 20% / … / 100% -> 定位完成
任务进度：1%（GUI 启动） -> 逐帧修复与编码的实际输出进度 -> 100%（任务完成）
```

## 回归验证

新增 `test/test_content_repair_progress_bridge.py`：在消费者刻意变慢、队列仍存在积压时依次写入 `1/25/50/75/100` 和 `FINISH`。测试断言 `wait_for_finish()` 返回时五个进度都已经回调，证明任务结束不会再截断队列尾部的进度事件。

`test/test_precise_mask.py` 还覆盖动态 OCR 的反馈边界：OCR 扫描不会发送任务进度事件；开始写出修复帧后任务进度才从实际帧比例前进到 `100%`。视频扫描过程则必须输出定位日志。

可执行以下命令验证：

```powershell
python -m pytest test/test_content_repair_progress_bridge.py -q
```

## 结果

内容修复任务的百分比会随着后端实际写出的帧持续更新；动态 OCR 的定位扫描仅通过日志明确呈现，随后才显示修复写出进度。正常结束时，队列中的最终 `100%` 事件也能到达界面。用户停止任务或子进程异常退出时，超时兜底仍会释放消息桥，避免引入新的后台线程残留。
