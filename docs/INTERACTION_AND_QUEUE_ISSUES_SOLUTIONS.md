# 交互响应、配置同步与动态任务队列问题整理

## 背景与目标

CleanCanvas Studio 包含三个独立的媒体操作页面：

- **内容修复**：对图片或视频中的字幕、文字和符号区域执行修复；
- **画质增强**：对图片或视频执行 Real-ESRGAN 类增强；
- **图片转换**：执行本地图片格式与 ICO 尺寸转换。

这几页都包含耗时操作、配置项或任务状态。实际使用中出现的问题并不只是“界面卡顿”，而是包含了任务调度、配置快照和已审核 OCR 结果的生命周期。本文记录问题、根因、最终约束和对应解决方案，作为后续维护时的行为基线。

## 1. OCR 检测期间界面无法操作

### 现象

在内容修复页点击“检测当前帧 OCR”后，PaddleOCR 的模型加载和推理会长时间占用资源。用户可能无法流畅地拖动预览、切换任务或操作其它控件。

### 根因

早期实现将 OCR 放在 Python 线程中。尽管主逻辑不在 Qt GUI 线程内，模型导入、Python 解释器锁竞争，以及 OCR 原生计算对 CPU 的占用，仍可能使主事件循环得不到足够调度时间。

### 解决方案

1. 单帧 OCR 改为在独立 `multiprocessing.Process` 中运行；子进程不访问任何 Qt 控件。
2. OCR 结果序列化为多边形字典，通过进程队列返回。
3. GUI 主线程使用 Qt 定时器非阻塞轮询结果，并在主线程更新选框、任务状态和提示条。
4. Windows 下将 OCR 子进程设为低于正常优先级，减少 CPU 饱和时的交互迟滞。
5. OCR 执行期间仅禁用“检测当前帧 OCR”以阻止重复提交；其它页面交互保持可用。
6. 如果用户在 OCR 完成前切换任务，结果保存到发起检测的任务；再次选择该任务时按该媒体自身的预览比例回显。

### 最终规则

OCR 是可取消/可等待的后台计算，不是 UI 锁。任务切换不会丢失结果，关闭窗口会终止尚未结束的 OCR 子进程并释放 IPC 资源。

## 2. 待处理任务没有正确跟随配置修改

### 现象

用户添加任务后，在点击“运行”前修改 AI 设备、修复/增强模型、倍率、模型目录或视频 OCR 策略。旧实现中，不同页面的行为不一致：有些任务过早冻结配置，有些则到运行时才读取全局配置，导致用户难以判断实际生效的值。

### 根因

任务队列缺少统一的配置生命周期：

- 内容修复任务创建时 `options` 为空，部分配置在“确认修复区域”时才写入；
- 画质增强任务在添加时保存模型、倍率和设备，之后设置变化不会同步；
- 画质增强运行时直接读取全局模型目录，而不是任务快照；
- 图片转换没有任务队列，配置在转换按钮点击时读取，但日志没有完整记录实际参数。

### 解决方案

#### 内容修复

- 文件加入任务列表后立即写入运行快照：修复模式、AI 设备、模型目录和视频 OCR 策略；
- 在任务仍为“待处理”时，修改上述设置会自动同步全部待处理任务；
- 每次同步都在日志面板输出“配置项、新值、受影响任务数”；
- 已经进入“处理中”的任务继续使用启动时的快照，不受后续设置修改影响。
- 进入处理中前会复制 `Task.execution_options`；即使 Qt 的状态更新尚在事件
  队列中，后续配置同步也只能改写仍待处理的任务，不能改写该次执行。

#### 画质增强

- 任务快照包含增强模型、输出倍率、AI 设备和模型目录；
- 修改这些设置时自动同步所有待处理任务；
- `MediaEnhancer` 使用 `task.model_dir`，而不再在执行时重新读取全局模型目录；
- 添加任务、同步设置、重置任务和开始任务均输出完整的实际配置。
- 增强器创建前会冻结 `EnhanceTask.execution_options`，使每个任务的模型、
  倍率、AI 设备与模型目录彼此独立。

#### 图片转换

- 图片转换不维护任务队列；格式、质量和 ICO 尺寸在点击“转换并保存”时读取，因此此前的界面修改会自然生效；
- 开始日志会记录输出格式；JPEG/WebP 额外记录质量；ICO 额外记录所选尺寸。

### 与 OCR 审核相关的安全规则

不能把任何配置都当成普通字符串直接覆盖。以下设置会改变实际擦除区域：

| 配置变化 | 对待处理内容修复任务的处理 |
| --- | --- |
| 修复区域编辑方式、矩形扩边、笔刷半径、颜色筛选参数 | 仅影响当前未确认草稿；已经确认的组合 `MaskPlan` 保留其序列化参数，运行时不被后续设置反向改写 |
| OCR 像素阈值、OCR 候选置信度阈值、OCR 轮廓外扩比例 | 清空旧 OCR 候选，要求重新检测；已确认的组合 `MaskPlan` 不受影响 |
| 动态 OCR 字幕像素精细定位及其颜色/容差/描边参数 | 同步待处理任务的动态 OCR 执行快照；已经开始的任务继续使用启动时快照 |

这样既避免“界面显示了新 OCR 规则，实际却运行了旧检测结果”，也保证红色组合 mask 与子进程实际执行的冻结计划一致。

## 3. 任务状态被页面级“当前任务”变量间接影响

### 问题

队列调度器通常只会同时运行一个媒体，但这不意味着所有任务应该共享同一份
运行状态。页面级的“当前处理索引”若同时被用于预览、进度、状态判断和配置
读取，就会在异步 Qt 信号尚未到达时让后续任务被错误地当作当前项。

### 解决方案与边界

- `Task.status`、`Task.progress`、`Task.execution_options` 是内容修复每个任务
  自己的状态；`EnhanceTask` 也拥有相同职责的 `status`、`progress` 和
  `execution_options`；
- 状态、进度、完成和失败信号全部携带稳定的任务索引，直接更新对应行；
- 内容修复的 `current_processing_task_index` 以及画质增强的预览索引只负责
  定位实时预览、滑块和停止按钮，不能作为任务状态或配置的来源；
- 调度队列只决定**下一个**应启动的任务，不会把排队任务改为“处理中”。

因此，单个任务运行时，后续行仍保持各自的“待处理、0% 和独立执行快照”；
它们不会继承前一行的进度、状态或模型设置。

## 4. 内容修复运行中新增任务的状态和调度不正确

### 现象

内容修复开始后仍可以添加媒体，但旧实现只在点击“运行”时取得一次待执行任务索引。运行期间添加的任务无法进入当前批次；并且新增文件的预览加载会改变当前页面状态，容易让用户误以为新任务被初始化为“处理中”。

### 根因

执行线程迭代的是启动时固定的 `pending_task_indices`，而不是可追加的调度队列。任务列表虽然允许新增行，但新增行与当前运行批次没有关联。

### 解决方案

1. 内容修复改用 `queue.Queue` 保存待执行任务索引，并通过锁保护“队列是否仍接收新任务”的状态。
2. 点击运行时，只将当时已经审核通过的待处理任务加入队列。
3. 运行中新增文件时，任务对象按默认状态创建为**待处理**，不会发出“处理中”状态更新。
4. 新任务完成 OCR 检测或手动选框后，用户点击“确认修复区域”；如果当前队列仍在运行，该任务会被追加并在当前任务完成后自动执行。
5. 队列判空与追加任务使用同一把锁，防止刚确认的新任务在队列收尾时被遗漏。
6. 用户点击停止后，队列停止接收追加任务；新任务保持待处理，下一次点击运行再处理。

### 最终规则

内容修复不能在没有修复区域审核的情况下自动运行。新增任务的正确状态是“待处理”，而不是“处理中”；“确认修复区域”才是进入当前执行队列的门槛。

## 5. 画质增强运行时禁止新增任务，队列无法动态使用

### 现象

画质增强任务运行时，“打开”按钮被禁用，任务列表整体也被禁用。用户无法继续添加媒体；即使能够添加，旧执行逻辑也只处理启动时存在的任务。

### 根因

`start_queue()` 同时存在两个限制：

1. 调用了 `add_button.setEnabled(False)` 和 `task_list.setEnabled(False)`；
2. 使用启动时固定的 `pending_task_indices` 进行 `for` 循环。

### 解决方案

1. 运行时保留“打开”按钮和任务列表可用；
2. 使用线程安全的 `queue.Queue` 替代固定索引列表；
3. 用户新增媒体后，任务以“待处理”状态创建并立即追加到正在运行的增强队列；
4. 当前任务完成后按 FIFO 顺序自动处理新增任务；
5. 删除和重置操作仍由任务列表的运行状态保护，防止修改已入队索引；
6. 停止请求发出后，队列不再接收新任务，未开始任务保留待处理状态。

### 最终规则

画质增强是可动态追加的 FIFO 队列。用户无需等待长视频结束才能继续添加下一项，但不能在运行过程中删除或重置已调度的任务。

## 6. 子进程日志只出现在控制台，进度停在 1%

### 现象与判断

Paddle 的“跳过模型站点连通性检查”“没有 ccache”等信息是提示或警告，通常
不是进度固定在 1% 的直接原因。看到 `Subtitle Removing: 0%` 说明子进程已经
进入修复流程；真正的问题是早期的跨进程桥可能在末尾消息尚未分发时被停止，
而第三方库直接写入 stdout/stderr 的信息又没有进入 GUI 日志板。

### 解决方案

1. 子进程在所有进度、日志、预览消息之后发送 `FINISH`；父进程等待消息桥
   消费到该哨兵，不能在 `Process.join()` 后立即停止消费者。
2. 修复子进程的 stdout 与 stderr 被按行转发到 GUI 日志板；Paddle 初始化
   警告、模型加载异常和普通 print 输出都可见。
3. tqdm 的逐帧回车式输出不写入日志板，以免淹没正常日志；进度条仍由稳定
   任务索引对应的 `progress_signal` 更新。

如果进度仍长时间不变，日志板现在会显示模型初始化、首帧推理或实际异常，
而不再只能从启动控制台猜测原因。

## 7. 任务状态转换总览

```text
内容修复
新增媒体
  -> 待处理（未审核）
  -> OCR 检测 / 手工选框
  -> 确认修复区域
  -> 待处理（已入当前队列或等待下一次运行）
  -> 处理中
  -> 已完成 / 失败 / 停止后待处理

画质增强
新增媒体
  -> 待处理（立即入当前队列；若队列正在运行）
  -> 处理中
  -> 已完成 / 失败 / 停止后待处理
```

## 8. 日志约定

以下事件必须在所属页面的日志面板中可见：

- 新任务创建时的配置快照；
- 待处理任务因设置变化被同步时的配置、新值和受影响任务数；
- OCR 或掩膜规则变化导致的“重新检测”或“重新确认”要求；
- 任务追加到当前队列；
- 任务开始时的实际执行配置；
- 队列完成、停止以及任务失败原因。

日志的目的不是重复进度条，而是让用户能够核对“这个任务为什么会以这个配置、在这个顺序执行”。

## 9. 验证建议

建议至少覆盖以下场景：

1. 运行内容修复任务时新增媒体：新增行应为“待处理”；确认区域后应在当前任务结束后开始。
2. 运行画质增强视频时点击“打开”并添加第二个媒体：打开按钮可用，第二项应自动接续执行。
3. 已加入多个待处理任务后更改 AI 设备、修复/增强模型、倍率或模型目录：日志应报告同步数量，所有尚未开始任务使用新值。
4. 已确认 OCR 掩膜后修改掩膜模式或 OCR 阈值：任务不得静默执行旧结果，应要求重新确认或重新检测。
5. 在队列停止请求后新增任务：新增任务应保留待处理，不能错误进入正在收尾的批次。
