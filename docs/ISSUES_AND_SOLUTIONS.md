# CleanCanvas Studio：问题、根因与解决方案记录

> 本文记录项目从“简单字幕去除器”升级为“图片/视频内容修复与画质增强工具”过程中发现的问题、处理方法、验证证据与仍然存在的能力边界。它既是维护记录，也可用于答辩、排障和后续需求评审。
>
> 状态含义：`已解决` 表示当前代码与默认测试已覆盖；`受限` 表示问题来自算法或外部依赖的客观边界，已提供提示或替代方案，但不能承诺完全消失；`待规划` 表示有明确方向但尚未实现。

## 2. 修复能力与掩膜问题

### P-01：仅使用 OpenCV 修复复杂画面效果差

**现象**

旧项目只有 `cv2.inpaint(..., INPAINT_TELEA)`。它对小字幕、纯色背景有效，但在二次元图片中的发丝、线稿、渐变、纹理和人物遮挡区域容易出现模糊、拉伸或错误补全。

**根因**

Telea 是传统局部像素修复算法，不具备语义理解能力；它只能从遮罩边缘附近的像素向内传播信息。

**解决方案**

建立统一 `InpaintEngine` 接口，保留 OpenCV 快速模式，并增加：

- LaMa：通用 AI 修复；
- Anime-LaMa：二次元图片/动画画面优先；
- Manga：黑白漫画线稿优先；
- OpenCV Telea：小区域、纯色背景、批量视频快速模式。

实现位置：

- `backend/inpaint/engine.py`
- `backend/main.py`

**验证**

- OpenCV 图片与视频回归测试通过；
- 本地历史 LaMa TorchScript 权重已完成 CPU 烟雾推理；
- AI 权重端到端测试使用环境变量显式开启，默认不下载模型。

### P-02：手工框选并不能真正去除 OCR 漏检内容

**现象**

旧流程中，用户框出的矩形仅用于限制 PaddleOCR 的检测范围。若文字、logo、拟声符号或装饰图标没有被 OCR 命中，即使用户手工框选，后端也不会生成修复 mask。

**根因**

“候选区域”和“最终擦除区域”被错误地混为一个字段，但实现上只把它当作 OCR ROI。

**解决方案**

引入明确的 `manual_regions` 与 `MaskPlan`：

- 手工矩形模式：框本身就是最终修复区域；
- OCR 多边形模式：框只筛选 OCR 候选；
- 混合模式：OCR 命中的内容使用精确多边形，未命中的手工框用于整块移除符号或 logo。

**验证**

默认测试验证手工区域可直接进入 OpenCV 修复，不依赖 OCR 二次命中。

---

### P-03：OCR 结果没有回显确认，用户无法控制误检

**现象**

OCR 发生在用户点击“运行”后的子进程中。用户无法预先确认、删除、移动或缩放检测框，误检结果会直接进入修复。

**解决方案**

将工作流改为：

```text
打开媒体
    -> 检测当前帧 OCR
    -> 回显候选框/多边形/最终 mask
    -> 用户编辑、清空或补充手工框
    -> 确认修复区域
    -> 批量运行
```

未确认任务不能进入批处理。编辑选框、参数或候选区域后，旧确认自动失效。

**实现位置**

- `ui/home_interface.py`
- `ui/component/video_display_component.py`
- `ui/component/task_list_component.py`

### P-04：PaddleOCR 已返回多边形，但项目把它压成矩形

**现象**

PaddleOCR `TextDetection` 可输出：

```text
dt_polys   文本多边形顶点
dt_scores  文本区域置信度
```

旧项目在 `backend/tools/ocr.py` 中把四个点转换成矩形，再填满整个矩形。斜体、倾斜字幕和靠近角色边缘的文字会多遮罩大量背景。

**解决方案**

新增：

- `OcrPolygon`：保存顶点与分数；
- `MaskPlan`：冻结最终掩膜计划；
- `polygon_mask()`：使用 `cv2.fillPoly()` 填充实际多边形；
- 可选 `refine_polygon_mask()`：在 OCR 多边形内按局部 Lab 色差与连通域细化；
- 红色半透明最终 mask 预览，青色线显示 OCR 多边形，黄色框显示候选 ROI。

**验证**

- 倾斜多边形掩膜面积小于外接矩形；
- ROI 只过滤多边形，不改写顶点；
- 伪造 `dt_polys` / `dt_scores` 测试确认顶点和分数不会丢失；
- 轮廓细化在高对比合成文字上能缩小掩膜，失败时回退原多边形。

---

### P-05：视频逐帧 OCR 精确但过慢

**现象**

30 FPS、10 分钟视频约有 18,000 帧。每帧运行 CPU PaddleOCR 会显著拉长处理时间。

**解决方案**

将“掩膜形状”与“视频 OCR 更新频率”拆分，提供三种策略：

| 策略 | OCR 调用量 | 场景 |
| --- | ---: | --- |
| 确认帧静态掩膜 | 1 次 | 固定字幕、固定台标，默认最快。 |
| 采样 OCR 多边形 | 每 N 帧 | 轻微移动字幕，兼顾速度和准确度。 |
| 逐帧 OCR 多边形 | 每帧 | 短片段、频繁移动文字，最慢。 |

**验证**

5 帧合成视频测试中：采样间隔 2 时 OCR 调用 3 次；逐帧策略调用 5 次。

## 3. 图片、视频与模型工程问题

### P-06：图片输出扩展名和实际编码不一致

**现象**

GUI 对图片输出路径使用 `.png`，但旧后端按源文件扩展名调用 `cv2.imencode()`。JPEG 输入可能生成“文件扩展名是 PNG、字节内容却是 JPEG”的文件。

**解决方案**

后端按 `video_out_path` 的实际后缀选择编码器，并对不支持后缀回退为 PNG。

**验证**

测试使用 JPEG 输入与 PNG 输出，检查输出文件头为：

```text
89 50 4E 47 0D 0A 1A 0A
```

即 PNG 签名。

---

### P-07：AI 模型没有统一的下载、校验和设备管理

**现象**

AI 修复与增强模型体积大，Torch/CUDA 环境也有差异。若 GUI 启动即加载模型，或者下载失败后留下半个文件，用户体验和稳定性都会很差。

**解决方案**

- 模型惰性加载；
- 下载到临时文件后再原子移动；
- MD5 完整性校验；
- 自动 / CUDA / CPU 设备选择；
- 可配置缓存目录；
- 高级设置显示模型状态并支持删除本程序下载的模型。

**边界**

MD5 是完整性检查，不是高对抗安全校验；正式发行可进一步使用 SHA-256、签名和版本清单。

---

### P-08：去文字和画质增强混在一起，增强任务无法批量管理

**现象**

修复任务需要 mask，输出通常保持分辨率；超分辨率任务不需要 mask，输出分辨率会变化。把它们塞进同一页面和队列会让参数、输出命名、进度和用户心智模型混乱。

**解决方案**

新增独立“画质增强”页面和 `MediaEnhancer`：

- Real-ESRGAN Anime；
- Real-ESRGAN General；
- 1×、1.5×、2×、3×、4×倍率；
- 图片增强；
- 实验性逐帧视频增强；
- 多媒体任务队列、进度、状态、日志和输出路径管理；
- 任务选择时显示输入/完成输出预览；视频处理期节流显示输入/当前输出对比；
- 输出命名为 `_enhanced_x{倍率}`，不覆盖源文件。

---

### P-13：增强完成后预览仍显示输入媒体

**现象**

增强页完成回调只显示“增强完成：输出路径”，但没有重新读取输出媒体，所以左侧预览仍是旧输入图。

**解决方案**

完成后：

- 图片：重新读取输出图片；
- 视频：读取输出视频第一帧；
- 更新预览标题为“输出”或“输出视频首帧”；
- 若读取失败，明确显示“输出读取失败”。

---

### P-14：图片任务错误显示为“正在逐帧增强”

**现象**

进度回调没有区分图片和视频，导致单张图片任务显示视频专用文案。

**解决方案**

按 `MediaEnhancer.is_picture` 区分状态：

```text
图片：正在增强图片……
视频：正在逐帧增强视频……
结束：正在写入输出文件……
```

### P-17：Real-ESRGAN 视频增强出现 inference tensor 原地修改错误

**现象**

增强视频时 GUI 显示：

```text
Inplace update to inference tensor outside InferenceMode is not allowed.
```

**根因**

模型输出在 `torch.inference_mode()` 内创建，但后处理在该上下文外执行：

```python
output.squeeze(0).float().cpu().clamp_(0, 1)
```

`clamp_()` 是原地操作，PyTorch 2.7 禁止在 inference mode 外原地修改 inference tensor。

**解决方案**

- 将推理、分块拼接、CPU 后处理放进同一个 `inference_mode()`；
- `clamp_()` 改为非原地 `clamp()`；
- 将后处理也纳入异常捕获，未来会显示项目级“Real-ESRGAN 推理失败”错误，而不是裸 PyTorch 异常。

**验证**

新增 `test_realesrgan_postprocess_accepts_inference_tensor`，显式构造 inference tensor 并验证处理成功。

## 4. 布局与界面体验问题

### P-11：QFluentWidgets 导入时输出推广日志

**现象**

启动 GUI 或导入后端配置时出现：

```text
QFluentWidgets Pro is now released...
```

**根因**

当前第三方库版本在导入 `qfluentwidgets.common.config` 时无条件执行 `print()`。

**解决方案**

在 `gui.py` 和共享 `backend/config.py` 中只对第三方导入阶段使用 `redirect_stdout(StringIO())`，不修改虚拟环境中的库文件，也不吞掉项目运行期日志和错误。

---

### P-12：增强页原型式布局与内容修复页视觉语言不一致

**现象**

长文件路径自动换行，右侧设置卡高度被撑大；预览区还设置了较大的最小尺寸。更重要的是，增强页使用普通 QLabel/QComboBox 原型控件，而内容修复页已使用 CardWidget、SettingCard、任务表和日志卡，两个页面看起来像不同应用。

**解决方案**

- 增强页重建为“左侧黑底 16:9 预览/日志，右侧设置卡/任务表/操作卡”的结构；
- 使用 `MediaPreviewComponent`、`CardWidget` 和 `ComboBoxSettingCard` 统一视觉语言；
- 文件路径进入任务表 tooltip，日志中保留完整路径，不再用长路径标签撑布局；
- 增强预览按窗口尺寸重缩放，完成后切换输出媒体。

---

### P-15：导航展开后窗口变大，收起后无法恢复

**现象**

点击左上角菜单后，QFluentWidgets 会把导航栏以内嵌 `322px` 侧栏形式展开。内容修复页已有预览与设置的最小宽度，Qt 为满足它们自动扩大顶层窗口；导航收起后 Qt 不会自动缩小顶层窗口。

**解决方案**

- 保留原版的内嵌 `322px` 导航展开策略；
- 将内容页最小宽度从约 `1198px` 降至约 `807px`，使导航展开时不再迫使窗口扩张；
- 窄窗口仍由 QFluentWidgets 自动使用菜单浮层；
- 移除视频预览 `960px` 最小宽度；
- 删除 resize 中的 `setFixedHeight()`；
- 新增 `AspectRatioContainer`，在可用空间中 letterbox 显示真实 16:9 画面。

**验证**

离屏测试中，窗口在 `1280px` 宽度下：

```text
初始：1280px
展开导航：1280px
收起导航：1280px
```

视频实际显示区域保持 16:9。

---

### P-16：右侧长说明与一行五按钮挤压视频预览

**现象**

在 `1108×758` 非全屏尺寸下，设置卡的长说明与五个同排按钮使右侧宽度达到约 `636px`，左侧视频区只剩约 `383px`。

**解决方案**

- 设置卡显示短摘要，完整说明移至 tooltip；
- 限制摘要和下拉框的展示宽度；
- 将五个操作按钮改为两行三列网格；
- 保持按钮文字完整，不依赖不清晰的缩写。

**验证**

在原先 1108px 窗口中继续压缩会让桌面工作台失去可用比例，因此项目改为采用参考版级别的最小工作尺寸。当前基线为：

```text
窗口最小尺寸：1360×720
折叠导航：视频区 835px，设置区 436px
展开导航：视频区 561px，设置区 436px
```

回归测试要求视频区大于设置区，且设置摘要不自动换行。

---

### P-18：竖屏图片或视频预览被固定 16:9 画布压缩

**现象**

内容修复页曾将所有输入先缩放、填黑边到固定 16:9 预览画布；增强页的黑底预览容器同样固定为 16:9。竖屏媒体虽然不会变形，但实际内容在宽黑框中显得过小，且坐标映射与画布比例不够直观。

**解决方案**

- `AspectRatioContainer` 支持运行时更新宽高比；
- 内容修复页按源帧 `width / height` 设置逻辑预览画布；
- 增强页在输入、输出和对比预览时按实际媒体比例更新显示区域；
- 横屏、竖屏、方形媒体均保持自身比例，布局只提供可用边界而不强制改变内容比例。

**验证**

使用 540×960 合成竖屏图像验证：内容修复和增强预览的逻辑/实际显示区域均满足“高大于宽”。

## 5. 产品身份、版本与开源合规

### P-09：缺少完整开源发行文件

**现象**

- `MODIFICATIONS.md`：重大改造记录；
- `THIRD_PARTY_NOTICES.md`：上游、IOPaint、Real-ESRGAN、模型和依赖边界；

**边界**

## 6. 仍然存在的限制与正确使用方式

### L-01：OCR 不是任意对象分割

PaddleOCR 的 `dt_polys` 是文本区域轮廓，不是字符笔画级语义 mask，也不能可靠识别人物、衣物、任意图标、复杂背景花纹或所有艺术字。

**当前缓解措施**

- OCR 多边形；
- OpenCV 局部轮廓细化；
- 手工矩形；
- OCR + 手工矩形混合模式；
- 用户确认红色最终 mask。

**后续方向**

笔刷/橡皮擦像素级 mask、SAM 等交互式分割插件。

---

### L-02：单帧 AI 模型处理视频可能闪烁

LaMa、Anime-LaMa 和 Real-ESRGAN 都主要面向单帧图像。逐帧运行时，即使每帧结果都看起来合理，相邻帧生成的纹理也可能不同。

**当前缓解措施**

- 在 UI 中明确提示；
- 视频提供静态、采样、逐帧 OCR 策略；
- 长视频优先使用 OpenCV 或短片段验证 AI 效果；
- 保留 A/B 区间以分段处理。

**后续方向**

引入 ProPainter 等时序模型、光流传播和跨帧一致性约束。

---

### L-03：视频音频回封装有输入格式边界

视频处理后会尝试复制原音频并回封装。某些无音频、编码不兼容或容器异常的输入文件无法直接导出 AAC/MP4 音频流。

**当前行为**

音频回封装失败时，保留已经成功编码的视频画面，并记录明确错误，不覆盖原始输入。

**后续方向**

支持多音轨、字幕流、章节、元数据复制，以及音频转码回退策略。

---

### L-04：模型权重的再分发权需要逐个核验

模型包装代码可使用开源许可证，但模型权重、训练数据、示例媒体和 logo 可能使用不同协议。

**当前策略**

- 默认不提交大模型权重；
- 用户按需下载；
- 记录 URL 和 MD5；
- 在 `THIRD_PARTY_NOTICES.md` 说明需要在离线安装包发行前单独核验权重许可。

```powershell
.\.venv\Scripts\python.exe -m unittest test.test_ai_integration_optional -v
```

## 8. 维护原则

后续新增功能时，应优先检查以下问题：

1. 它的状态由谁拥有，是否有唯一事实来源？
2. 是否会阻塞 GUI 主线程？
3. 是否需要线程、进程、Queue 或 Qt Signal？
4. 用户能否在执行前看到实际会修改的区域？
5. 小窗口、长路径、多语言和高 DPI 下布局是否仍然可用？
6. 输出是否覆盖原文件，失败时是否会留下损坏正式文件？
7. 是否引入新的第三方代码、二进制、模型或许可证义务？
8. 是否已有一个不下载模型、不依赖网络的回归测试？

这些检查不能保证项目永远没有问题，但能让问题在进入用户机器之前更早暴露。毕竟，修复工具最不该做的事，就是先把自己的界面和输出修坏。
